# Relay channel key provisioning

This daemon half targets the suite-A codec frozen at
`531a46b6bbb9e8286c42f9ad60476d4332d792aa`. Nothing under
`packages/protocol/relay/` changes. The identity successor statement is a separate,
versioned signed record, not a change to the Noise handshake or record framing.

## Two keys, different custody

The warm X25519 static key authenticates this daemon on a Noise IK channel. It is
generated by the daemon's CSPRNG and kept in a profile-scoped OS keychain entry or
an explicitly selected private file. Losing this key never silently generates a
replacement for an existing pin.

The Ed25519 identity private key belongs off the execution machine, generated by
an external signer. The daemon accepts only its public half. It never generates,
imports, stores, or signs with that identity private key. The older same-host
custody discussion in S0.2 section 4 is superseded by the off-machine decision.
Public bytes cannot prove where their private counterpart was generated or kept;
that physical separation remains the operator's responsibility.

Keeping both private keys on the stolen disk would remove R2's recovery advantage.
An existing daemon skill-signing key is therefore not reused as this identity.

## Provision and restart

Set `DOMOVOI_RELAY_IDENTITY_PUBLIC_KEY` to the external signer's canonical,
unpadded base64url Ed25519 public key before starting the daemon. It must encode
exactly 32 bytes and a nontrivial point in the prime-order subgroup. No secret
environment variable is accepted for either relay key.

Without `DOMOVOI_RELAY_CREDENTIAL_FILE`, the OS keychain must answer. The keychain
service is `domovoi-relay`; its account is a SHA-256 digest binding the resolved
profile home and machine id. A locked, unavailable, or failed keychain refuses
provisioning or startup. There is no automatic disk fallback.

An explicit absolute `DOMOVOI_RELAY_CREDENTIAL_FILE` selects file storage, even
when a keychain exists, matching the CLI credential policy. A profile-local path
such as `.domovoi/relay-channel.key`, expressed as an absolute path, keeps the
warm file with the profile. The printed warning names daemon impersonation, not
the different authority of a paired client bearer. Unix file checks reject group
and other mode bits before reading. Windows retains the CLI policy's limitation:
mode 0600 is not an ACL proof. Leaf symlinks, nonregular files and identity changes
between lstat and open refuse. Parent-directory trust is required.

The profile's `.domovoi/relay-identity.json` contains only a versioned public pin
and custody selector: machine id, Ed25519 public key, generation, suite and X25519
public key, plus the explicit file path when selected. File credentials carry
only the warm private key and its machine/public-identity bindings. File reads
are capped before allocation: 1 KiB for the credential and 8 KiB for the public
record. The same limits apply to publication.

The profile lease is held before any key read or publication. The secret is
stored and read back before the public record is atomically published. An
interruption between those writes can reuse the already stored secret for the
same machine and identity, avoiding another key generation. Missing, malformed,
or mismatched credentials on a provisioned profile refuse. Changing the configured
identity or custody also refuses; neither implicitly rotates or moves a key.

After provisioning, startup reads the saved custody choice and public pin even
when the two environment settings are absent. Service configuration retains only
the public key and explicit path. Unprovisioned profiles with neither setting
remain direct-only and never probe the relay keychain.

The production factory passes the loaded private key to the existing relay
admission constructor and wipes its own byte buffer after the constructor copies
it. The server wipes its copy on stop. If startup stops waiting for an in-flight
credential operation, its lease remains held until that operation settles, and
any late key result is wiped. Native keychain calls may block; the deadline cannot
interrupt a synchronous OS call. JavaScript strings and OS-managed copies cannot
be reliably wiped by this implementation.

## Signed successors

`relayIdentityPinSchema`, `relaySuccessorStatementSchema`, and
`relaySignedSuccessorSchema` validate strict bounded public records. The signature
is canonical unpadded base64url for 64 bytes. A statement contains version 1,
machine id, identity public key, next generation, previous channel public key,
and the new suite/channel public key.

`relaySuccessorSigningBytes` returns UTF-8 bytes of the exact prefix
`domovoi.relay-channel-successor.v1\0`, followed by compact JSON for this array:

```text
[version, machineId, identityPublicKey, generation, previousChannelPublicKey,
 suite, responderPublicKey]
```

The external signer signs those bytes with Ed25519. There is no signing API that
accepts its private key in the daemon. `verifyRelayChannelSuccessor` uses the
already pinned identity, strict Ed25519 verification, the exact predecessor and
machine id, and a generation exactly one greater than the accepted generation.
It rejects exhausted counters, replay against the advanced pin, unchanged keys,
low-order channel points and noncanonical X25519 aliases. It returns the new
public pin only after every check passes.

`verifyRelayProfileSuccessor(homeDirectory, envelope)` binds that verifier to the
saved daemon public record. It is read-only and works even if the warm credential
is missing or the keychain is locked. Verification does not adopt a successor or
consume a statement. A future adoption path must atomically persist the returned
pin before using it; repeated verification against the same old pin is not a
replay ledger. The factory also exposes its public pin as `relayIdentity` on the
local handle. Existing strict pairing responses are unchanged.

## Evidence and remaining boundary

Protocol tests sign through Node's Ed25519 implementation, then verify through
the noble implementation. They pin the signing domain/field order and reject
tampering, wrong machine, wrong identity, replay, overflow, private fields and
key aliases. Custody tests inject locked and failed keychains, failed publication,
failed read-back, missing/tampered keys and cancellation. Production factory tests
generate and reopen an actual stored channel key and verify the key supplied to
the server, including buffer cleanup and the lease during cancellation.

This is custody and statement verification. Client identity-pin enrollment,
successor delivery, persistent adoption, rebuilt-host rotation, and the relay
server are not implemented here. The stolen-disk launch row is not closed merely
by provisioning keys. A client must retain its authentic identity pin separately
from an attacker-controlled daemon profile before R2 can protect its recovery.

The shared `@getdomovoi/credential-store` package is publishable. It is bundled
into daemon dist, with `@napi-rs/keyring` still a daemon runtime dependency. The
protocol-only runtime lock retains its single-archive format.
