# S0.7 — security review brief

Send-ready. One engagement, fixed scope, fixed commit.

---

## What we are asking for

A security review of Domovoi's Noise IK **composition** at a frozen commit, and a written
finding list we can publish.

The code is an application-level composition over audited primitives. We are not asking for
a review of the primitives. We are asking whether the way they are assembled is sound.

## The artefact

| | |
|---|---|
| Repository | `github.com/getdomovoi/domovoi`, public, Apache 2.0 |
| Path | `packages/protocol/relay/` |
| Commit | `531a46b6` |
| Size | about 230 lines of composition, plus test-only wire-format fixtures |
| Language | TypeScript, running on Node and React Native |
| Primitives | `@noble/curves`, `@noble/hashes`, `@noble/ciphers` |

The wire format is frozen at that commit and pinned by checked-in byte fixtures, so the
files reviewed will still be the files shipped. A `node:crypto` backend exists in the tree
as a **test-only comparison path** and is not reachable at runtime; it is in scope only as
a question of whether that isolation holds.

Supporting document, in the same repository: `S0.2-RELAY-CRYPTO.md` — threat model, what
the relay sees, forward secrecy, rotation and recovery, and the three designs we chose
between. Read §1 and §5 first.

## In scope

1. **Handshake composition.** Noise IK as implemented: message patterns, key derivation,
   transcript hashing, the initiator and responder state machines.
2. **Nonce and state management.** Nonce derivation and exhaustion, rekeying, replay
   across reconnects, state reuse between sessions.
3. **Cross-runtime behaviour.** The same composition runs under Node and React Native.
   Whether entropy sourcing, timing and constant-time behaviour hold on both.
4. **Test-path isolation.** Whether the comparison backend is genuinely unreachable in a
   production build.

## Out of scope

- The noble primitives themselves. Curve, hash and cipher implementations are assumed sound.
- Key custody, rotation and successor adoption. These are real and reviewable, but they do
  not exist at `531a46b6`. See the second engagement below.
- Admission and transport binding, for the same reason.
- The relay server. It is a separate closed repository and holds no plaintext by design;
  reviewing it is a later, separate engagement.
- Application code outside `packages/protocol/relay/`.
- Penetration testing of hosted infrastructure. None is deployed.

## A second engagement, to quote separately

Two areas we want reviewed and cannot freeze yet, because the code is still landing:

- **Key custody boundaries.** A two-key split: a warm channel key in the daemon profile and
  a cold identity key held off the machine. Whether rotation and successor adoption preserve
  the property that a stolen disk does not yield the identity key.
- **Transport binding and admission.** Whether the handshake is correctly bound to the outer
  transport, and what a malicious relay can do with routing metadata it legitimately sees.

These live in `packages/protocol/relay-admission/` and `apps/daemon/src/relay-provisioning.ts`.
We will name a frozen commit once adoption lands. Quote it separately, or indicate what it
would add to the first engagement if run together.

## Threat model, in short

The relay is **untrusted infrastructure we operate**. It brokers connections between a
user's own machines and must not be able to read what it carries. Clients are open source,
so any claim about payload confidentiality must hold against a reviewer reading them and
must not depend on the relay behaving well.

The adversary we care most about: someone who obtains a machine's disk. We have designed
for that with a cold identity key. We want that design attacked.

Known and accepted: the relay sees routing metadata, which is also what billing requires.
Phone clients store their key in application storage rather than a hardware enclave, and the
consequences of that are written out in `S0.2-RELAY-CRYPTO.md` §9.

## Deliverables

1. A findings report with severities and reproduction steps.
2. A remediation round: we fix, you verify.
3. Permission to publish the report, including any unremediated findings.

Point 3 is not negotiable in the other direction. We would rather publish a report with
open findings than hold a clean one back.

## What we need in the quote

- Price and duration, fixed against commit `531a46b6`.
- Who does the work, and their prior Noise Protocol Framework work specifically.
- Whether remediation verification is included or billed separately.
- Earliest start date.

## Context worth knowing

We considered adapting an existing reviewed Noise implementation instead of reviewing our
own. The strongest candidate, Snow, was the subject of a Trail of Bits review in 2024, but
its maintainers still state it has received no formal audit, so we did not treat that report
as one either. Adapting it would also have meant a native binding layer on three runtimes.
That is why we are here rather than consuming someone else's audited library.
